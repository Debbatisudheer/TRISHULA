# TRISHULA V0.9.100 — Live Command / Execution Updates

V0.9.100 extends the verified Mission Control WebSocket stream with live command lifecycle and command execution updates. V0.9.99 telemetry streaming remains available and its telemetry stream contract remains `v0.9.99`.

## Flow

`Command API / Scheduler / Orchestrator -> durable GroundRecord -> Kafka -> KafkaConsumer -> command execution projection -> WebSocket Gateway -> Mission Control clients`

The existing command validation, scheduling, retry, timeout, dead-letter, and execution reconciliation boundaries are preserved. V0.9.100 only projects already-accepted command lifecycle/execution records onto the Mission Control real-time transport.

## WebSocket messages

Command lifecycle/execution messages use:

- `type=mission_control.command_execution`
- `stream_version=v0.9.100`
- `protocol_version=trishula-ws-v1`
- mission/source/record/sequence/timestamp/correlation identifiers
- `command_id`, `command`, `target`
- `lifecycle` when present
- `execution_state` when present
- `event_type`, `vehicle_response`, and `severity` when present
- the original command/event fields under `fields`

Examples of projected execution states include `ACKNOWLEDGED`, `EXECUTING`, `COMPLETED`, `FAILED`, `TIMEOUT`, `REJECTED`, and `CANCELLED`.

## Filtering boundary

Only command lifecycle records and event records explicitly classified with `event_class=COMMAND` are projected. Unrelated event and telemetry records are not converted into command execution messages.

## Compatibility

- `trishula-ws-v1` remains the WebSocket protocol.
- V0.9.99 telemetry messages continue to use `mission_control.telemetry` and `stream_version=v0.9.99`.
- V0.9.100 command execution messages use a separate `stream_version=v0.9.100`.
- Existing REST resources and command state machines remain intact.
