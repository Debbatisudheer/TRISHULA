# TRISHULA V0.9.110.1 — Telemetry Sliding Window DSA

## Objective
Optimize the existing ground-side telemetry state path for rolling telemetry statistics without replaying the complete telemetry history for every new sample.

## Real TRISHULA problem
Telemetry is a continuous stream. Mission operators need recent-window statistics such as rolling average and change across recent samples. Recomputing a window by scanning every retained sample on every telemetry record is O(k) per update.

## DSA implementation
Added a fixed-size ring-buffer sliding window per mission/source/metric.

- Ring buffer append/eviction: O(1)
- Running sum update: O(1)
- Rolling average: O(1)
- Latest-minus-oldest delta: O(1)
- Memory: O(k), bounded by the configured window size
- Default window size: 32 samples
- Late/out-of-order sequence numbers are rejected from the window

The durable telemetry history is unchanged. The window is derived operational state.

## Integration
The window is maintained by `MissionStateEngine` after accepted telemetry processing and is exposed additively as `telemetry_windows` in mission/vehicle state summaries.

Each summary contains:
- metric
- count
- capacity
- average
- latest
- delta
- last sequence
- window version

Version: `v0.9.110.1`.

No changes were made to spacecraft/rover physics, mission execution, science processing, Kafka contracts, PostgreSQL schemas, or UI data paths.

## Validation
The isolated Go window tests pass in the local environment. The local benchmark shows the O(1) ring-buffer update path versus full-window recomputation. Full Ground Data Service tests require the project's Go 1.25 toolchain; this environment only has Go 1.23.2 and cannot download Go 1.25 due network restrictions. UCRT64 validation is required before freezing the checkpoint.
