# TRISHULA V0.9.109.1 — Mission History Top-K Heap DSA Optimization

## Baseline

V0.9.108.1 — Ground command scheduler min-heap DSA optimization.

## Why this checkpoint changes direction from a new event scheduler

TRISHULA already has a persistent command scheduler in `services/ground-data-service/command_scheduler.go`. It is the existing mission scheduling boundary and was optimized in V0.9.108.1.

Creating a second independent mission-event scheduler would duplicate scheduling ownership. Instead, V0.9.109.1 applies DSA to another real hot path that already exists: bounded operational history queries.

## Real project problem

`applyQuery()` previously collected every matching durable record, sorted the complete result set newest-first, and only then applied `Limit`.

For a large mission history where an operator requests a small page such as the newest 50 records, the service could therefore sort thousands or millions of matching records even though only the top 50 are returned.

Previous path:

```text
all durable records
      ↓
filter
      ↓
all matching records
      ↓
full sort O(m log m)
      ↓
keep first k
```

where `m` is the number of matching records and `k` is the requested limit.

## DSA improvement

When `Limit > 0` and the input is larger than the requested page size, V0.9.109.1 uses a fixed-size binary min-heap containing the best `k` records seen so far. The implementation uses direct slice-backed heap operations so the bounded selection path does not introduce per-record interface allocations.

The heap root is the worst retained record. A new matching record replaces the root only when it is better according to the existing query ordering:

1. newest mission timestamp first
2. newest sequence number first
3. lexicographically smallest record ID for an exact tie

After scanning the input, only the retained `k` records are sorted for the final API order.

New path:

```text
all durable records
      ↓
filter
      ↓
Top-K min-heap of size k
      ↓
final sort of ≤ k records
      ↓
API result
```

## Complexity

For `m` matching records and requested limit `k`:

- Previous: `O(m log m)` sorting and `O(m)` retained memory before truncation.
- New bounded-page path: `O(n log k)` heap selection plus `O(k log k)` final ordering, with `O(k)` retained selection memory.
- The asymptotic improvement is about bounded selection and memory; wall-clock speedup is workload- and implementation-dependent and is not claimed as a fixed multiplier.
- `Limit == 0` keeps the existing full-result behavior and sorting path.
- If the input contains `k` or fewer records, the existing full-sort behavior is retained because a heap provides no benefit at that size.

The improvement is therefore most relevant to large histories with small operational page sizes.

## Behavioral preservation

The checkpoint preserves:

- all existing query filters
- cursor semantics
- newest-first ordering
- sequence-number tie ordering
- deterministic record-ID tie breaking
- `Limit == 0` full-result behavior
- repository interfaces
- durable storage behavior
- command scheduling
- Kafka contracts
- Mission Control API shapes
- spacecraft/rover physics and science behavior

No new mission-state owner is introduced.

## Tests added

`query_topk_test.go` verifies:

- Top-K output matches the established ordering
- deterministic record-ID tie breaking
- query filters remain active
- zero-limit behavior remains unchanged

`query_topk_benchmark_test.go` provides a diagnostic comparison between the bounded Top-K heap path and the previous full-sort path over 100,000 records with a limit of 50. It also reports allocations so the memory-retention improvement can be observed.

The benchmark is diagnostic only. It does not establish a fixed speedup across machines; the important invariant is correctness plus the `O(n log k)` / `O(k)` bounded-selection behavior.

## Scope

This checkpoint is a ground-data-service query optimization. It does not alter the physical mission model, autonomous rover navigation, science processing, communications model, database schema, Kafka topic contract, or Mission Control UI data path.
